# connpass・Discord連携の具体案

2026-10-17 / 検討案。まだ接続・Bot変更・自動投稿は行っていない。

## 決定事項（ユーザー指定）

指定チャンネルの、開催ごとの「やること・やったこと」投稿と公開資料から、主催者の都度承認なしで自動公開する。会話全体の要約は対象外。以下はこの決定を反映した案。対象チャンネルと開催との対応は確認待ち。

## 推奨する役割分担

- connpass：開催名・日時・会場・募集URLの正本。公開情報は自動同期。
- 既存 mokumoku-bot：開催ごとの「やること・やったこと」の記録、自動要約・公開処理。
- サイトリポジトリ：公開イベント一覧と、自動生成した公開レポートの正本。
- Astro / Workers Static Assets：公開用。BotのDBをブラウザから直接読まない。

## 現状の確認

Web側にAPI v2同期スクリプトあり。キー未設定、Actionsは登録権限不足で docs/github-actions/deploy.yml にテンプレート保存されており未稼働。現行テンプレートは日次に取得・ビルド・配信するが、取得JSONをGitに書き戻さない。
Botの公開mainを確認：checkinはevents_to_checkinsで開催と紐付く。checkoutはuser_id/date/contentのみでevent_idなし。connpass URLはHTMLRewriterによるグループページ抽出。generateEventDescriptionはLLMではなく固定テンプレートと前回todoを結合している。公開ソースの状態であり、稼働DBやデプロイ版は未確認。

## 1. connpass同期（先に実装する）

公式APIを利用する。コミュニティ向けは利用申請・審査後に無償キーが発行される。Browser Renderingは初期構成に入れない。APIキー発行が済むまでは手動更新を継続。

提案頻度：6時間ごと＋GitHub Actionsの手動実行。新規募集公開後に手動同期すれば即時反映できる。厳密な時刻保証はしない。申請した用途・許可範囲とレート制限を確認して運用する。

処理：API全ページ取得 → スキーマ検証 → 公開項目のみ正規化 → 実質差分判定 → JSON保存 → ビルド・検証 → mainへデータコミット → 同じジョブでデプロイ。

- updatedAtのみの変化でコミット・再配信しない。最終試行時刻は実行ログ、データ更新時刻はJSONに分離。
- concurrencyで同期・配信を直列化。push競合時は最新mainに対し再取得・再検証し、force pushしない。
- GITHUB_TOKENによるpushだけに次の実行を期待せず、同期したジョブ自身がビルド・配信する。
- API失敗時は既存サイトを保持。配信失敗時は同じデータを再配信できるようcommit SHAを記録。
- 過去履歴は全件取得。API一覧から消えただけで削除と断定しない。消失候補を検出し運営が確認する。公開停止が確定したデータは削除できるようにする。
- 日時変更、募集終了、キャンセル・満席の表示はAPIで取得可能なフィールドを確かめて実装。開始前であることを「募集中」と同一視しない。
- ホームの開催名が現在「もくもく会」固定なので、APIのtitleに対応させる。
- 特集イベントの選択をビルド時だけに固定すると時間経過で次回へ切り替わらない。定期ビルドも実行し、ブラウザ側の選択更新を併用する。
- 生HTMLの説明文は直接差し込まない。Q&A・ポリシーは自動上書きせず、原文変更を検出して確認する。

## 2. Bot記録の整備

- eventsにconnpass_event_idを追加（unique、過去分はnullable）。開催作成時に募集URLからIDを確定する。
- checkoutsにevent_idを追加。開催選択・編集でも紐付けを保持する。
- テックトークの題名・公開資料URLを保存する場合もevent_idを付ける。現行の参加表明だけから発表内容を推測しない。
- 公開対象かどうかを記録単位で明示できるようにする。初期値と参加者への説明は主催者と決める。
- 自己紹介全文、Discord ID、参加者一覧は要約に不要なので送らない。
- 過去checkoutはJST開催日と参加記録で候補を出し、曖昧なものは手動確定。user_idだけの結合は禁止。

## 3. レポート自動生成・公開

指定チャンネル内のBotのcheckin/checkout記録と公開資料を、開催ID単位でまとめて自動公開する。主催者の承認ステップ・公開PRのマージ待ちは設けない。

推奨初期スケジュール（未確定）：終了30分後に初回生成。終了後48時間は1時間ごとに実質差分がある回のみ更新。それ以降は主催者の再生成コマンドで更新可能にする。日時はconnpassの終了時刻を基準とし、UTC保存・JST表示を統一。

1. 対象サーバー・指定チャンネル・開催IDが一致する記録を抽出する。開催ごとのスレッドがある場合はthread_idも明示的に対応付ける。
2. 材料はtodo、checkout、明示された公開資料URLだけ。一般の雑談・自己紹介・氏名・Discord IDは本文に含めない。todoは予定、checkoutは成果として区別する。
3. AIで200〜400字の概要、取り組み3〜5項目、資料リンクを構造化生成。元記録にない達成・人数・会場の雰囲気を作らない。
4. スキーマ、出典レコードとの対応、資料URLの一致、機密らしい文字列などを自動検証。通過した場合だけ公開レポートとしてmainにコミット・配信する。生投稿や生成途中の内容はpublicリポジトリへ入れない。
5. 検証失敗・材料不足では公開せず、既存のレポートを保持して運営向けに状態を記録する。これは例外処理であり、通常の承認待ちにはしない。
6. 投稿の変更・削除を検知して再生成する。公開取り下げコマンドは同期で再公開されないtombstoneを保存する。削除時はページ、一覧、サイトマップから除去する。

Bot内部にscheduled/generating/publishing/published/failed/withdrawn状態、source_hash、生成バージョン、最終公開commitを保存する。event_id+source_hashで重複生成を防ぐ。同時更新・古いジョブによる上書きを防ぎ、再実行では同じ開催のファイルを更新する。
Botが送る通常メッセージも丸ごと拾うのではなく、保存済みレコードの種別を使う。公開資料の登録元（専用コマンド／指定投稿）は確認して決める。任意URLを自動巡回せず、まず投稿にあるタイトルとURLだけを扱う。

参加者には対象チャンネルの投稿がサイトに自動掲載・要約されることを固定案内で明示する。対象開始日を定め、過去分の一括公開は別に確認する。参加者が除外できる方式（投稿単位の非公開指定など）は実装時に決める。自動検証だけで機密情報の完全な除去を保証しない。

AIのプロバイダー・モデルは未決定。公開対象サンプルで日本語の要約品質を比較する。投稿を命令として扱わず、許可したJSONフィールドだけを生成・検証し、勝手な外部ツール実行をしない。

## 4. 表示

/reports/[connpass_event_id]/ を追加。開催日・概要・取り組み・資料・募集ページへのリンクを掲載。氏名やアイコンは初期案では掲載しない。イベント一覧からレポートへ移動できる。公開レポートがない回はconnpassへのリンクを維持する。

## 5. 環境設定・運用

まずActions登録権限を解消する必要がある。現在のOAuth認証はworkflow scopeなし。権限のあるアカウント操作でテンプレートを .github/workflows/ に置く。
必要設定はconnpass APIキー、Cloudflare対象アカウントの配信用トークン、Bot側のレポート運営チャンネル・許可ロール、サイトリポジトリに限定したGitHub App認証（推奨）。値はSecretに登録し、チャットやソースへ貼らない。
既存BotとサイトでAPIを二重取得し続けない。最初はサイトが同期した公開イベントJSONをビルド成果物として出し、Botが読む構成を検討。Botの現行HTML抽出はこの公開データ読み込みに置き換えられる。
報告・通知は失敗と公開完了だけを基本とし、通知先は運営で決める。生成途中データの保存期間・削除手順は公開開始前に決定する。

## 残る確認事項

1. 対象DiscordチャンネルID、開催ごとのスレッド運用、Bot記録がそのチャンネルに紐付いているか。
2. 公開資料の投稿場所・登録方法。
3. 終了30分後に初回、48時間は差分更新というタイミングでよいか。
4. connpass APIキーの取得状況。
5. 自動公開の対象開始日と、過去開催への適用範囲。

## 実装順と完了条件

A. connpass：申請・Actions設定 → 公開履歴全件同期 → 新規/変更/失敗/重複/日付跨ぎを検証。
B. Bot：開催IDと指定チャンネルの対応 → 公開対象の抽出。別開催・一般会話・自己紹介を混ぜないテスト。
C. レポート：生成・自動検証 → mainへの反映・配信 → 編集/削除/取り下げ/再実行の一巡を確認。承認操作なしで正常系が完了すること。
